# Data model (PostgreSQL 18)

The central database behind the API ([ADR-0002](adr-0002-agent-platform.md)). This is the design;
the EF Core migrations of phase 1 implement it and this file follows them.

## Conventions

- **Keys:** time-ordered UUIDv7 `uuid`, generated by the API (`Guid.CreateVersion7()`); the migrations set no
  database default, so a raw SQL insert must pass the id. The event table uses `bigint` identity.
- **Time:** `timestamptz`, always UTC. Shown as `dd/mm/yyyy` on the web (global #12).
- **Additive only** (global #4): no column or table is dropped, renamed or retyped. A row is retired by a
  status or a `*_at` column, not deleted, except where retention or an account deletion requires it.
- **Closed sets** (a status, a role) are `text` with a `CHECK`; the code holds the same values as an enum
  with a `default` branch (global #11). A set that grows with the product (`harness_kinds`) is a table.
- **Tokens and codes** are stored as SHA-256 hashes, never in clear.
- **Search** is case- and accent-insensitive (global #13): one normaliser in the API fills the `*_search`
  columns, and searches compare normalised text.
- **Paging** is by key (`last_event_at`, `id`), newest first; no list is unbounded.
- **Foreign keys** on every reference, none cascading.
- **Authorisation:** every team-owned row carries `workspace_id`, and every query filters by the caller's
  membership. Nothing is readable without it (global #6).

pair and marks the old one `replaced_by`; a reused, already-replaced refresh token revokes the agent's tokens.

- **Tags, note, services, projects (ADR-0008 phase 1b, migration `MachineFacts`).** `tags` and `admin_note` are typed by a workspace admin
  (audited; only the note's length is in the audit trail) and are untrusted text wherever Claude reads them. `share_services` is the machine
  owner's opt-in (default off, enabling needs the re-authentication of a grant); while it is off no service is stored, and turning it off drops
  `services`. `machine_projects` has one row per (agent, project key): a session that reports a project key creates it (`session`), the
  agent's reading of a listed folder updates it (`listed`); the folder path itself never reaches the server. `remote_runs` gains `project_key`
  (≤ 200), `kind` (`test`, `build`, `deploy`, `other`; CHECK `ck_remote_runs_kind`) and, for a finished `test` run of a known tool, the parsed
  `tests_passed`, `tests_failed`, `tests_skipped` (NULL when not recognised); index (`target_agent_id`, `project_key`, `created_at` DESC) WHERE
  `project_key IS NOT NULL`. **Retention:** `machine_projects` rows are deleted after `retention_days` without a sighting. **Export** adds
  `machineProjects` and the run's `projectKey` and `kind`. **Account deletion** deletes the user's machines' project rows, clears their
  `services` and `share_services`, and empties the `project_key` of the user's runs.

`workspace_settings` gains `alert_cpu_pct`, `alert_memory_pct`, `alert_disk_pct` (default 90, 1-100),
`alert_sustain_seconds` (default 300, 60-86400) and `remote_runs_enabled` (default false). New columns carry
database defaults, so an older API keeps inserting rows.

**Script runs (ADR-0008 phase 2, migration `ScriptRuns`).** `remote_runs.mode` gains `script` (the mode CHECK and the shape CHECK are dropped and
re-added: a script run has no `argv`, `shell_command` or `cwd`; an emptied run keeps its shape), and the table gains `script_interpreter`
(`sh`, `bash`, `powershell`, `python`; CHECK), `script_body` (text; emptied on account deletion, exported), `script_args` `text[]`,
`target_environment` and `target_function` (the effective role frozen at creation, part of the approval hash), `approved_with_totp`
(boolean, default false), `output_cap` (bytes, 1-64 MiB, the workspace limit frozen at creation; NULL for argv and shell runs) and the
output account: `output_read_bytes`, `output_dropped_bytes` (as the target reports them), `output_refused_bytes`, `output_missing_from_seq`
(what the server refused over the cap, always one range from a chunk on), `output_chunks` and `output_complete` (NULL for argv and shell
runs; true only when nothing was dropped, refused or stopped at the read limit). `workspace_settings.script_output_max_bytes` (default 8 MiB;
CHECK 1-64 MiB; set by an admin in the remote settings).

**Files and stdin on a script run (ADR-0010 §2, migration `ScriptRunFiles`).** `remote_runs` gains `script_files_json` (jsonb: the run's text files as `[{path, text}]`, sorted by path; null for none) and `script_stdin` (text; null for none), with a CHECK that only a `script` run carries either. The
hash of a run with files or stdin uses the tag `script2`; one without keeps `script1` and its old bytes. `agents.capabilities` may now contain `script_files`, which an agent reports when it writes a script's files and stdin; the API refuses a run with either to an agent that does not (`files_unsupported`).
Both columns are cleared by account deletion and included in the export.

**Asks across machines (ADR-0008 phase 3, migration `MachineAsks`).** `agents` gains `accepts_asks` (boolean, default false: the machine owner's opt-in),
`accepts_asks_set_at` and `accepts_asks_set_by` (FK users). New table `machine_asks`: `id`, `workspace_id`, `requester_agent_id`, `requester_user_id`,
`requester_session_id` (FK sessions), `target_agent_id`, `target_user_id`, `target_session` (the Claude session that received it), `client_key`,
`project_key`, `question` (1-8000; NULL once emptied), `status` (`queued`, `delivered`, `answered`, `no_idle_session`, `not_accepting`, `no_answer`,
`expired`, `cancelled`; CHECK), `answer` (≤ 100 000; NULL once emptied), `answer_truncated`, `error`, `created_at`, `expires_at`, `received_at` (migration `AskReceivedAt`: when the target daemon said it holds the ask; the status stays `queued`), `delivered_at`,
`answered_at`, `ended_at`; CHECKs `requester_user_id = target_user_id` and `requester_agent_id <> target_agent_id`; UNIQUE (`requester_agent_id`,
`client_key`); indexes on (`target_agent_id`, `status`) WHERE open, (`requester_agent_id`, `created_at`) and (`workspace_id`, `created_at` DESC). The
question and the answer are personal data like a command: exported (`asks`), emptied on account deletion and the rows deleted after `retention_days`
past their end; the audit rows name an ask by id only. Every transition is a compare-and-set; the housekeeping loop expires a queued ask after 30 minutes (2 before 19/10/2026)
and a delivered one after 15 without an answer, and member removal, an agent move or revoke, the opt-in turning off and the workspace switch turning off
cancel the open ones.

**Agent actions (ADR-0005 amendment, migration `AgentActions`).** New table `agent_actions`: `id`, `workspace_id`, `agent_id` (FK agents), `requested_by` (FK users, the machine's owner),
`kind` (`restart`, `update_check`, `update`, `status`; CHECK), `status` (`queued`, `delivered`, `succeeded`, `failed`, `expired`; CHECK, default `queued`), `result` (the agent's text, ≤ 2000;
it can name the machine's folders, so it is exported to its requester and emptied on account deletion), `created_at`, `expires_at` (created + 10 minutes), `delivered_at`, `finished_at`;
UNIQUE (`agent_id`, `kind`) WHERE status IN ('queued', 'delivered') (one open action of a kind per agent) and an index on (`agent_id`, `created_at` DESC, `id` DESC). Every transition is a
compare-and-set (`queued → delivered → succeeded | failed`; an open action past `expires_at` becomes `expired`); finished rows are deleted after `retention_days` by the housekeeping loop.

- **Transitions are compare-and-set** (`UPDATE … WHERE status = <expected>`); a run, its audit row and a grant's
  use count change in one transaction; the API publishes to the stream after commit.
- **Output** is masked by the target, at most 1 MB per run (checked atomically with the chunk insert), never logged,
  and never carries a NUL byte. Audit rows name a run by id and command hash, not its argv.
- **Retention:** metrics 7 days; runs with their output, and resolved alerts, after `retention_days`; deletes run in
  batches. Grants and jobs are configuration: retired, never deleted. Removing a member or moving an agent revokes
  its grants, retires its jobs, resolves its alerts and cancels its open runs.

- **`session_events` is the record**; tasks, subagent runs, usage and the session's status are projections
  updated in the same transaction as the batch that carries the events.
- **Idempotency** sits in `agent_batches`, not in the event table: a unique key on a partitioned table must
  include the partition key, so it cannot catch a retried batch that lands in another month.
- **Retention:** every few hours a job writes each workspace-day older than `retention_days` (UTC, by `received_at`)
  to one zipped JSON array, records it in `event_archives`, and deletes those rows in the same transaction.

## 5. Commands from the web

| Table | Columns | Keys and indexes |
|---|---|---|
| `session_commands` | `id`, `workspace_id`, `session_id`, `agent_id`, `kind` (`prompt`, `stop`), `body`, `created_by`, `created_at`, `expires_at`, `status` (`queued`, `delivered`, `applied`, `failed`, `expired`, `cancelled`), `delivered_at`, `applied_at`, `result`, `transport` (`hook`, `inbox`, `channel`; nullable: how an applied command reached its session, as the agent reported it; on a `delivered` command `inbox` or `channel` means it was written into the session and not shown yet) | (`agent_id`, `status`) WHERE `status IN ('queued', 'delivered')`; (`session_id`, `created_at` DESC) |

| `permission_requests` | `id`, `workspace_id`, `session_id`, `agent_id`, `tool_name`, `tool_input` `jsonb`, `status` (`open`, `answered`, `expired`), `created_at`, `expires_at`, `decision` (`allow`, `deny`), `reason`, `answered_by`, `answered_at` | (`session_id`, `status`) |

The API accepts a command or a permission answer only from the session's owner (`agents.user_id` of the
session's agent).

**Claude's answer to a command is a view, not a status.** `applied` means the hook handed the text to the session; it
does not say Claude has answered. `GET /sessions/{id}/commands` adds three fields to each row, computed from
`session_events` and never stored: `replyEventId` (the event), `replyText` (its first 300 characters) and `replyMore`
(the message goes on). A command's reply is the first `transcript` event of the same session that is an assistant
message with a non-blank text block and was written after the command's `applied_at`. "Written" is the transcript
line's own `timestamp`, else the event's `occurred_at` (the agent stamps an event with the moment it READ the line,
which can be later). Only an `applied` `prompt` has one; two commands applied together share the first reply written
after them; an event shortened to a marker (`truncated`) carries no message and is skipped. The web shows
Applied -> "waiting for Claude's reply" -> "Claude replied" from these fields; `session_commands.status` keeps its
six values. `applied_at` is the moment the hook handed the command to the session: the agent sends it as `at` with its
`applied` report (the report itself can come seconds later) and the API believes it unless it is older than the command
(give or take `ClockSkewMax`, 2 minutes), never later than the report; an older agent sends none and `applied_at` is the
report's time. The search reads at most `ReplyScanMax` events (500) from the oldest applied command in the page.

- **Nothing is deleted:** a project, an application, a component and an issue are archived, a release is cancelled (one that went out stays), and a name
  is free again once its holder is archived. A `project_members` row, an `issue_links` row, a test case and a code link are removed outright (they are links, not records).
- **Rights** are computed in the API (`ProjectAccess`) from the workspace role and the project role; the workspace membership check comes
  first, so a person who left the workspace loses every project at once. A workspace `viewer` never changes anything.
- **Caps stand in for paging** on the small lists: 100 active applications per project, 200 components and 200 releases per application, 50 links, 100 test cases and 50 code links per issue.
- **Issue numbers and positions** are given under a row lock on the project (`SELECT … FOR UPDATE`), so parallel creates get distinct numbers; a move writes the middle of its neighbours and spaces the whole project again when the gap is gone.
- **Audit** rows (`project.*`, `application.*`) name a row by id and carry no typed text. Account export and deletion for these tables are
  not decided yet (ADR-0011 §5): the rows keep the deleted user's id and hold no personal fields of their own.

## Your data: export and account deletion

- **Export** (`GET /api/me/export`): one JSON file, streamed: the profile, sign-in providers, memberships, machines,
  commands sent, the user's own audit trail, and every session run on the user's machines with its tasks, usage and
  events.
- **Deletion** (`POST /api/me/delete`, with the password when there is one and the word `DELETE`): refused (409
  `sole_owner`) while the user is the only owner of a workspace that has other members. Otherwise, in one transaction:
  the personal fields are cleared (`users.email`, name, password hash; status `deleted`), provider links deleted,
  login sessions, mail tokens, agents and agent tokens revoked, open invitations to the address revoked, memberships
  ended, workspaces with no other member archived; the captured content of the user's sessions is deleted (events,
  tasks) or emptied (titles, subagent descriptions, command bodies, permission inputs). Ids, times, usage and audit
  rows stay, so other people's records still make sense. The address is free for a new sign-up.
- **Archives too:** the day files already written past retention are rewritten without the user's sessions' events
  (a file left empty is deleted with its row), and their `event_archives` rows get the new count, size and SHA-256.
  Copies already taken off the server by the backups age out with the backups' own retention.

**Job schedules, signed approvals and the run account (ADR-0010, migrations `JobSchedules` and `ApprovalKeys`).** `job_schedules` (`id`, `workspace_id`, `job_id`, `target_agent_id`, `owner_user_id`, `kind` (`interval`, `daily`), `interval_minutes` (15 to 10080) or
`daily_at_minutes` (0 to 1439, UTC), `status` (`active`, `paused`, `ended`), `pause_reason`, `next_run_at`, `last_run_at`, `last_run_id`, `last_run_settled`, `failures_in_arow`, `created_at`, `updated_at`; CHECKs for the status, the kind and its
